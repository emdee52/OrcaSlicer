# PF-10-multisupport - multi-pass support collision avoidance

- Source: design follow-up to PF-10-paint / PF-10-auto (no fork release note; Orca-native).
- Branch: `port/PF-10-multisupport`, stacked on `port/PF-10-auto-fix`.
- Category: B/D. Status: **implemented, build clean; runtime/print pending.**

## Problem

The multi-pass painter (`PrintObject::_generate_support_material`) runs one engine pass per painted
support type plus a default pass, then merges the results. Each pass projects the *other* passes'
painted facets as blockers, but nothing stops a pass from generating support **into the support
geometry another pass already produced** - the supports physically overlap, waste material and
create collisions.

## Verdict on the two options

- **Merge bases then branch per region**: rejected. It would require a new unified support engine
  that grows a shared base and forks into per-style branches; neither the classic nor the tree
  engine works that way, and a tree "branching out of" a normal pillar is not a shape either
  engine can express. High risk, poor predictability.
- **Separate bases + awareness (chosen)**: each pass treats the supports already generated by
  earlier passes as obstacles, keeping the support/object XY gap. This reuses the exact mechanism
  already ported for PerObject Support (SU-1), which injects per-layer occupancy polygons into the
  support collision volumes.

## Design

SU-1 already feeds `OrcaExt::neighbor_occupancy(object)` (other objects' bodies + generated
supports, per object layer) into:
- the classic engine's `polygons_trimming` (`SupportMaterial.cpp`),
- the tree engine's `TreeSupportData::calculate_collision` (`TreeSupport.cpp`),
- `TreeModelVolumes` as an extra collision-only outline group (`TreeModelVolumes.cpp`).

This change generalizes that channel to include **the same object's earlier passes**:

1. `PrintObject` gets a transient `support_pass_obstacles` (per object-layer `Polygons`, local
   frame) with accessors in `Print.hpp`.
2. `OrcaExt::support_layers_occupancy(object, layers)` builds that footprint from an explicit set
   of support layers (islands + base + tree roof/floor areas), z-mapped onto the object layers.
3. The dispatcher publishes the composed prior-pass supports just before each pass
   (`set_support_pass_obstacles(...)`); the engine constructors read it through
   `neighbor_occupancy`, which now unions it in **independently of the PerObject Support toggle**.
4. Pass order is **explicit painted styles first, default pass last**, so painted regions are
   authoritative and the automatic/default supports build around them. The default pass still
   blocks every painted facet.

No new config keys. Nothing is painted => the legacy single-pass path runs unchanged
(byte-identical).

## Risks / known gaps

- Over-trimming: at a boundary between two styles, the later pass may lose support it "wanted";
  the earlier pass's support stays. Thresholds (`gap_xy_scaled`, tree `m_xy_distance`) are the
  existing support/object gaps, not a new tunable.
- Tree obstacles are collision-only (the neighbor outline group keeps
  `support_material_buildplate_only = true`), so prior supports never become placeable surfaces.
- Runtime/print geometry is unverified; this is a support-engine change and needs a print test
  with two adjacent painted styles (e.g. Grid next to Organic).
