# SU-14 - Support Zones: the overhang map must use the plate, not the object's own axes

- Source: `NEOTKOCM_RELEASE_2_47.md` ("The overhang map follows the object's rotation").
- Fork: `OrcaFS-NeotkoCM` @ `3bd92365d0` (2.4.7). Base for this diff: Snapmaker `v2.4.0`.
- Category: B (a bug fix). Status: **ported** on `port/SU-14` - build clean, `ctest` 2407/2407,
  runtime/visual check pending.
- Marker: `[ORCAPORT:SU-14]`.

## The bug

`SupportZoneProbe` measures "is this surface facing down" by casting a vertical ray per grid cell
and filtering facet normals by their Z. It built its meshes with `its_transform(part,
v->get_matrix())` - the volume's own matrix, which carries **no instance rotation**. So "down"
meant down in the **object's** local frame, before the user's rotation.

Consequence: rotate a part 90`°` (the release note's example is a surfboard standing on its edge)
and the map marks a flat **side** as needing support, and the "this zone catches nothing" warning
fires (or fails to fire) wrongly. The printed support was never affected - this is a render and
warning path only.

## The fix (verified against the fork)

Three layers, and the important part is that it is **backward compatible by default**:

1. `collect()` takes an orientation and applies it in front of the volume matrix:
   `its_transform(part, orient * v->get_matrix())`. Meshes, and therefore the rays and the normal
   filter, are now in **world orientation**.
2. `probe_zone`, `probe_object_coverage` and `sterile_zones` take `const Transform3d &orient`
   **defaulting to `Transform3d::Identity()`** - identity reproduces the old behaviour exactly, so
   any caller that does not pass it is unchanged.
3. The **callers** pass the instance orientation (the instance matrix with its translation zeroed)
   and, because the samples now come out already oriented, they add **only the instance
   translation** when drawing instead of multiplying by the whole matrix.

Fork evidence: `SupportZoneProbe.{hpp,cpp}` (the `orient` parameter and the `collect` transform),
`GLGizmoSupportZones.cpp` (the `orient_of` lambda plus `probe_zone(*mo, *v, step, orient)`), and
the drawing sites in `GLCanvas3D.cpp`.

## Deliberate limitation (inherited from the fork, documented not fixed)

The orientation passed is that of `instances.front()`. A multi-instance object whose instances
carry **different rotations** still probes each zone once, with the first instance's orientation.
The fork accepted this ("lo normal es una instancia, así que el coste no cambia"); the alternative
is one probe per instance, which multiplies the AABB work. Recorded here rather than silently
inherited - raise it if a real case appears.

Also unchanged from the port: the probe is render-only and never decides that support is needed
(see the patent boundary note at the top of `SupportZoneProbe.hpp`).

## Verification

- **Off-check:** with one instance and **no rotation**, the map and the warning must be identical
  to before. The `Identity()` default makes every untouched caller byte-identical by construction;
  the one behavioural change is the rotated case, which is the bug.
- **The fix:** rotate a part 90`°` about X and confirm the map follows the plate (the release
  note's surfboard case) and that the "catches nothing" warning agrees with a slice.
- Build clean + `ctest`. No unit test exists for the probe (no test callers), so this is a manual
  visual check; the automation is the MCP path (load a model, open the zones gizmo, read the gap
  state) once a fixture with a known rotation is picked.
